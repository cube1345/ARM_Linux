# 并发模型设计：i.MX6ULL 多线程 vs Windows 多进程

> 目的：解释本项目「板端单进程多线程 / Windows 多进程 / 跨机分布式」的并发架构，
> 以及「什么场景选多线程、什么场景选多进程」的判断方法。
> 依据：仓库 `apps/PhotoAlbum`（video_player / music_player / main_window）+ `qt/windows/run_all.ps1` 等。
> 适用：简历项目经历 / 面试问答（"单核为什么要多线程"、"多线程 vs 多进程怎么选"）。

---

## 一、总览：这套系统用的是"三层并发"

```
┌────────────── 板端 i.MX6ULL（单进程多线程）──────────────┐
│  主线程①  UI / Qt 事件循环 / watcher 回调                 │
│     ├─ ② VideoDecodeThread  视频：拉流+软解+伴音          │
│     ├─ ③ AudioDecodeThread  音乐：解+播                  │
│     └─ ④⑤ QtConcurrent      图片异步解码（临时线程）      │
└──────────────────────────────────────────────────────────┘
        │ RTSP / HLS / HTTP（网络，跨机）
        ▼
┌────────────── Windows 服务链（多进程 + 多核并行）─────────┐
│  ffmpeg×N（每路摄像头一个转码进程）  mediamtx.exe          │
│  stream_server.py   snapshot.py   grid_mjpeg.py           │
└──────────────────────────────────────────────────────────┘
```

关键认识：**"板端单进程多线程 + Windows 多进程 + 跨机分布式"三者不是风格选择，是结构决定的**。

## 二、单核为什么还要多线程（并发 ≠ 并行）

### 概念辨析

|          | 并行 parallelism       | 并发 concurrency             |
| -------- | ---------------------- | ---------------------------- |
| 含义     | 同一时刻多个线程真在跑 | 多个线程交错执行，调度器分时 |
| 必要条件 | 多核                   | 任意（单核即可）             |
| 本项目   | ❌ 没有                | ✅ 板端全靠它                |

单核上"多线程"本质：**操作系统把 CPU 切成毫秒级时间片，轮转分给各线程**，一秒内 A→B→A→B 快速切换，宏观上"都在跑"。

### 单核多线程的三个真实收益

1. **等待时让出 CPU，别人能干活**（最重要）
   代码里有大量"等"，不是"算"：

   - `av_read_frame` 等 NVR 网络数据（阻塞 IO）
   - `snd_pcm_writei` 等声卡消费缓冲
   - 文件播放按 fps `QThread::msleep` 节流
     如果解码和 UI 在一个线程，解码卡在网络 → **UI 一起卡死**，触摸无响应。
     拆线程后：解码线程等在网络上时，调度器把 CPU 让给 UI 线程，触摸照常响应。
     → **单核多线程最大的价值：别让一个线程的等待拖死整个程序。**
2. **抢占式调度保证 UI 能插队**
   Linux 调度器可抢占：即使解码线程在算（CPU 密集），时间片到了被强制切走，UI 线程拿到片就能响应触摸。不拆线程就没这个效果。
3. **职责分离 → 代码/排障清晰**
   解码线程管"拉流→解→发帧"，UI 管"收最新帧→画→响触摸"，接口只剩 `frameReady(QImage)` 一个信号。断流重连、状态机都在一个线程内维护。

### 单核的代价与"减负"

CPU 总量只有一份，解码吃多了 UI 就饿。所以本项目大量设计本质是**帮单核省 CPU**：

| 设计                          | 目的                                                    |
| ----------------------------- | ------------------------------------------------------- |
| 推流`scale=480:270`         | 单核软解上限 ≈ 480×270，再高解码线程占满 CPU、UI 卡死 |
| `latest-frame` 丢帧、不排队 | 解码跟不上宁可丢，不让缓冲积压占 CPU/内存               |
| 音乐预解码成 WAV              | 单核解 MP3 占满 CPU，预转 PCM 后播放几乎不耗 CPU        |
| 摄像头 HEVC → 服务端转 H.264 | 板端软解不了 HEVC，且转码放 Windows 做，不抢板端这颗核  |
| `rw_timeout` + 轮询退出     | 防止 ffmpeg 网络阻塞时白占线程不退，把 CPU 让出来       |

## 三、板端并发设计详情

### 并发单元全景（不是只有音视频）

| 并发单元              | 触发场景                           | 实现                                            | 常驻? |
| --------------------- | ---------------------------------- | ----------------------------------------------- | ----- |
| ① 主线程             | 全部 UI / 事件循环 / 触摸 / QTimer | ——                                            | 是    |
| ② VideoDecodeThread  | 视频页 / 监控单路 / 直播           | `class VideoDecodeThread : QThread`           | 是    |
| ③ AudioDecodeThread  | 音乐播放                           | `class AudioDecodeThread : QThread`           | 是    |
| ④ 图片解码（缩略图） | 相册缩略图网格                     | `QtConcurrent::run(&MainWindow::decodeImage)` | 临时  |
| ⑤ 图片解码（大图）   | 打开大图                           | `QtConcurrent::run(lambda)`                   | 临时  |

> 可见：并发不止音视频，还有**图片异步解码**（QtConcurrent 线程池）。Grep 证据：
> `main_window.cpp:2829 / 2873` QtConcurrent::run 两处。

### 分配原则

> **UI 一个线程 + 后台任务各自一线程，重活全放后台，UI 只收结果。**

```
UI 线程  ── 信号/槽(队列) ──►  收 frameReady QImage / watcher 完成回调
后台     ── 原子量 ──►        收 stop/pause/seek 请求
```

- 重活（解码/拉流/写声卡/解码图片）全不占 UI
- 短任务（图片解码）用完即退，常驻的只有解码两个线程
- 视频伴音（ALSA）在 VideoDecodeThread 内部做，与视频同源同步——**不是独立线程**

### 线程间同步手段（板端）

| 手段                                      | 用在哪                                                                     |
| ----------------------------------------- | -------------------------------------------------------------------------- |
| 信号/槽队列连接（主）                     | 解码线程→UI：frameReady/ended/positionChanged/fpsChanged                  |
| `QMutex frameMutex`                     | UI 侧 currentFrame 读写（onFrame 写、paintEvent 拷读），防绘制时换帧       |
| `QAtomicInt` + storeRelease/loadAcquire | 全部控制位：停止/暂停/seek/音频开关/音量——零阻塞，解码线程循环内顺路消费 |
| `wait()`                                | 析构/切源时安全回收线程                                                    |
| `QTimer`                                | 主线程刷新/统计/轮询，不开新线程                                           |

### 值得说的两个"为什么"

1. **为什么 seek/停止用原子而不是 stop→wait→start？**
   重启线程会阻塞 UI 且开销大。原子请求让解码线程在自己的循环里"顺路"响应，零阻塞、零锁竞争，还能边播边 seek。
2. **为什么音频 Master Clock 能控制视频？**
   解码线程内同时维护视频帧率节流 + 音频写卡，天然保持 A/V 时间线对齐；音频进度反推视频丢帧匹配。

## 四、为什么 Windows 侧是多进程（正好反证）

| 因素                       | Windows 侧的实际理由                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------- |
| **调用的是现成工具** | ffmpeg.exe / mediamtx.exe / python 都是独立外部程序，只能以进程方式调，塞不进我们的线程 |
| **故障隔离**         | ffmpeg 一路崩了，mediamtx/录像不能跟着死；进程独立崩溃、独立重启                        |
| **多核真实并行**     | Windows 机器多核，多进程能同时吃满多核；板端单核没这个动机                              |
| **独立部署/演进**    | 转码/分发/快照各自独立升级，还能跑在别的机器上（跨机分布）                              |

## 五、判断方法：多线程 vs 多进程

### 判断表

| 维度     | 偏多线程                      | 偏多进程                          |
| -------- | ----------------------------- | --------------------------------- |
| 数据交互 | 高频、大量、紧密（每帧/每包） | 低频、少量、松耦合（命令/URL）    |
| 隔离需求 | 崩了没关系 / 要共享状态       | 崩了一个不能拖垮全部 / 要安全隔离 |
| CPU 核数 | 单核（进程没并行红利）        | 多核想真并行                      |
| 调用对象 | 自己的代码逻辑                | 现成外部工具/第三方程序           |
| 生命周期 | 同产品同进退                  | 独立部署/重启/升级                |
| 内存资源 | 小、切换要省                  | 足、不在意页表开销                |

### 三个自问（设计/面试通用）

1. **"它们要不要频繁互相传大块数据？"**
   → 要（帧/包/实时状态）→ **线程**；不要（发命令/文件路径）→ 进程也可。
2. **"其中一个死了，另一个还能不能活？"**
   → 必须能活 → **进程**（隔离）；本来就要一起死 → 线程够。
3. **"我这颗是单核还是多核？"**
   → 单核 → **线程**（切换更省）；多核 + 要并行算 → 进程更稳（避开线程内存踩踏）。

### 一句话心法

> **共享数据流 → 线程；隔离/复用外部工具 → 进程；单核上优先线程，多核真并行才考虑进程。**

## 六、面试问答准备

**Q1：单核有必要多线程吗？**
有。多线程不是为"算得快"，而是解决"等待"和"响应"：让解码线程在网络/声卡/节流等待时把 CPU 让给 UI，触摸永远能插队；代价是 CPU 总量不变，所以同时用降分辨率、丢帧、预解码控制总占用。

**Q2：多线程 vs 多进程你项目怎么选的？**
板端全是"自己的代码 + 高频共享帧数据 + 单核受限" → 多线程正确；Windows 服务链全是"调现成工具 + 各管各 + 要独立重启" → 多进程必然。用"数据紧耦合要线程、故障隔离要进程、单核省切换要线程"三条答。

**Q3：怎么证明你的多线程没白做？**
解码线程等在网络上时，UI 触摸照常响应；解出来 `latest-frame` 直接覆盖，UI 永远拿到最新帧；`QAtomicInt` seek 不阻塞主线程——都是可验证的行为。
